# Release Note — v1 Contract (2026-09-12)

Branch: `feat/contract-v1`

## What changed

The protobuf contract now has a stable, versioned identity: `package api.v1`.
Every RPC lives under `/api.v1.*`, and the wire types that used to be
ad-hoc strings and ints are now first-class protobuf types. This is the
contract the SDKs build against; the friendly SDK surfaces callers already
use are unchanged.

### Typed statuses

`Request.status` and `Task.status` are enums (`RequestStatus`,
`TaskStatus`) instead of free-form strings. The canonical wire names are
`REQUEST_STATUS_PENDING` … `REQUEST_STATUS_DONE` and
`TASK_STATUS_PENDING` … `TASK_STATUS_DEAD_LETTER`. The maintained SDKs
keep exposing the friendly lowercase names (`"pending"`, `"done"`,
`"completed"`, …) and map at the boundary, so consumer code and the
conformance fixtures are unchanged.

### Timestamps

Every entity time (`created_at`, `updated_at`, `completed_at`,
`last_ping_at`, `revoked_at`, `lease_expires_at`) is a
`google.protobuf.Timestamp` instead of a server-formatted string. The
gateway emits RFC3339 strings; the gRPC SDKs render ISO-8601 strings, so
SDK callers still see text timestamps.

### Unified pagination

`ListRequests` and `ListUserSessions` share one pagination contract:
`page_size` plus an opaque `page_token`, and every response carries a
`ListPage{next_page_token, total_size}` trailer. `next_page_token` is
empty on the last page. This replaces the `limit`/`offset` pair on
`ListRequests` and the numeric `page_token` on `ListUserSessions`. The
token is opaque to clients — pass it back verbatim.

### Tool lookup and invocation

- `GetTool` resolves a tool by ID or by name in one RPC: set exactly one
  of `tool_id` / `tool_name` (the ID wins when both are set, an explicit
  both-set request is rejected with `INVALID_ARGUMENT`).
- `InvokeTool` is the v1 name for synchronous invocation.
- `ExecuteTool`, `GetToolById`, and `GetToolByName` remain as deprecated
  aliases with identical behavior, so existing callers keep working while
  they migrate. All three are marked `option deprecated = true`.

### Session-scoped credentials

`Session.api_key` is gone from the `Session` and `CreateSessionRequest`
messages. Session-scoped credentials are minted explicitly with
`CreateApiKey` (capabilities required) — a session no longer implies a
credential. `InvalidateSession` reports how many live API keys it
revoked, unchanged.

### Gateway routes

The HTTP gateway annotations are now part of the versioned contract. All
45 RPCs are POST. Most bind to `/api.v1/<Method>`; resource reads use
templated paths (`POST /api.v1/sessions/{session_id}`,
`POST /api.v1/sessions/{session_id}/requests/{request_id}`,
`POST /api.v1/users/{user_id}/sessions`, …) with `body: "*"`, so path
parameters and the JSON body merge. The SDKs target the templated routes.

## Bugs the migration surfaced

Moving the conformance suites onto the v1 wire found three server bugs,
all fixed here:

- **`UpdateRequest` stored the enum's numeric value as the status
  string.** The handler passed `model.RequestStatus(req.Status)` — a
  number-to-string cast — so a provider's "running" update stored
  `"3"`, which mapped back to `REQUEST_STATUS_UNSPECIFIED`. Requests
  appeared unspecified from claim until result submission, and
  status-filtered listings missed them. The handler now maps through
  the shared enum translation.
- **`GetTool` and `InvokeTool` were missing from the auth policy
  table**, so the new RPCs failed closed with "no auth policy
  configured" before the capability check could run.
- **The Python provider runtime polled with an invalid enum label**
  (`status="pending"` on `ListRequestsRequest`), which the proto layer
  rejects; the poll loop now sends the enum name.

## SDK migrations

- **Python**: statuses normalize through shared helpers (both
  transports deliver the friendly lowercase names), timestamps render
  as RFC3339 strings, `list_requests`/`list_user_sessions` take an
  opaque `page_token`, tool lookup goes through `GetTool`, and
  invocation posts to `InvokeTool`. The HTTP connection layer targets
  the templated gateway routes.
- **Go**: `ListRequests(status, toolName string, limit int32, pageToken
  string)` maps the friendly status name onto the wire enum;
  completion polling compares enum values; invocation calls
  `InvokeTool`.
- **TypeScript**: the client and conformance adapters map enum statuses
  and Timestamps to the same friendly model as the other SDKs; the MCP
  adapter hydrates stream chunks from the retained chunk window (the
  v1 request message no longer carries chunk payloads).

## Compatibility

This is a breaking wire change — that is the point of the versioned
package. Within it:

- The deprecated aliases (`ExecuteTool`, `GetToolById`, `GetToolByName`)
  behave identically and give callers a migration path.
- SDK-visible models (friendly status strings, text timestamps, request
  dicts) are unchanged; code written against the maintained SDK facades
  compiles and passes the shared conformance fixtures unchanged, except
  for the `list_requests`/`list_user_sessions` pagination parameters
  (`offset` → opaque `page_token`).
- The MCP gateway's JSON-RPC surface is unaffected; it maps onto the v1
  enums internally.

## Migration

- gRPC callers: rebuild stubs from `server/proto/service.proto`
  (`cd server && make gen-proto-all`) and treat status fields as enums.
- HTTP callers: switch the twelve resource-read calls from
  `/api.v1/<Method>` posts to the templated routes in the proto
  annotations; send enum names (`"REQUEST_STATUS_DONE"`) or numbers for
  status fields, never bare `"done"`.
- Pagination: replace `offset` arithmetic with the opaque
  `page.next_page_token` loop.
